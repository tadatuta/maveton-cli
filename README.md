# maveton-cli

CLI на строгом TypeScript для подготовки RSS подкастов. Принимает описание выпуска в YAML или JSON, создаёт новый RSS либо добавляет выпуск в существующий фид. Отдельная команда проверяет результат локально. Интерфейс, сообщения и документация — на русском языке.

Поддерживаются RSS 2.0, метаданные iTunes для Apple Podcasts и Spotify, RSS-сценарий импорта YouTube Music и **все 31 утверждённый тег Podcasting 2.0**, включая вложенные структуры. Устаревший `podcast:images` также поддерживается, с предупреждением. Версия спецификации зафиксирована; список тегов и атрибутов — в [справочнике](docs/PODCASTING2.md), источники и границы проверки — в [SOURCES.md](docs/SOURCES.md).

Инструмент работает с уже опубликованными HTTPS-ссылками. Он не загружает аудио, не публикует RSS, не регистрирует подкаст на платформах, не редактирует и не удаляет существующие выпуски. AI, учётные записи, API-ключи и `ffprobe` не нужны.

## Установка

Нужны macOS или Linux, **Node.js 24+** и npm. Для разработки рекомендуется версия Node из `.nvmrc`.

Из каталога проекта:

```bash
npm ci
npm run build
node dist/cli.js --help
```

Для работы из любой директории установите локально собранный пакет:

```bash
npm pack
npm install --global ./maveton-cli-1.0.0.tgz
maveton --version
```

Публикация в npm не выполнялась: используйте локальный tarball, а не `npm install -g maveton-cli` из публичного реестра. Если установка глобальных пакетов требует прав администратора, используйте Node через менеджер версий или запускайте `node /путь/к/maveton-cli/dist/cli.js` напрямую.

Во всех примерах ниже `maveton` можно заменить на `node dist/cli.js`, если текущая директория — каталог проекта.

## Быстрый старт: новый подкаст

1. Создайте шаблоны:

   ```bash
   maveton init --directory ./my-podcast
   ```

   Появятся `my-podcast/podcast.yaml` и `my-podcast/episode.yaml`. `init` создаёт описания, **не пустой RSS**: для публикации на платформах нужен хотя бы один выпуск. Существующие шаблоны команда не перезаписывает.

2. Отредактируйте оба файла. Замените все `example.com`, контакт, автора, обложку, даты и описание. Укажите фактический размер аудио в байтах. Шаблон содержит демонстрационные значения, включая прошедшую дату; их надо заменить.

3. Посмотрите план и проверьте метаданные:

   ```bash
   maveton add \
     --podcast ./my-podcast/podcast.yaml \
     --episode ./my-podcast/episode.yaml \
     --output ./my-podcast/rss.xml \
     --dry-run
   ```

4. Создайте фид и независимо проверьте его:

   ```bash
   maveton add \
     --podcast ./my-podcast/podcast.yaml \
     --episode ./my-podcast/episode.yaml \
     --output ./my-podcast/rss.xml

   maveton validate --feed ./my-podcast/rss.xml --strict
   ```

5. Разместите RSS самостоятельно по адресу `feedUrl`, затем отправьте этот адрес платформам. CLI ничего не отправляет на сервер.

## Добавление следующего выпуска

Создайте отдельный файл описания: новый `id`, новая ссылка на аудио, название и дата. Пример JSON — [examples/episode.json](examples/episode.json).

Из локального фида в **новый** файл:

```bash
maveton add \
  --feed ./my-podcast/rss.xml \
  --episode ./episodes/002.yaml \
  --output ./my-podcast/rss-next.xml

maveton validate --feed ./my-podcast/rss-next.xml --strict
```

Из удалённого RSS:

```bash
maveton add \
  --feed https://example.com/podcast/rss.xml \
  --episode ./episodes/002.json \
  --output ./rss-next.xml
```

Изменения метаданных подкаста в отдельном `podcast.yaml` не применяются к существующему фиду. В `add` нужно выбрать **ровно один** источник: `--podcast` для создания либо `--feed` для добавления. Старый RSS остаётся источником данных подкаста и истории выпусков.

## Перезапись с резервной копией

Любой существующий выходной файл защищён от перезаписи. Для намеренного обновления фида:

```bash
maveton add \
  --feed ./rss.xml \
  --episode ./episodes/002.yaml \
  --output ./rss.xml \
  --overwrite
```

Перед заменой CLI создаст рядом файл вида `rss.xml.bak-2026-11-06T09-00-00.000Z-a1b2c3d4` и сообщит его путь. Копия содержит исходные байты. При ошибках валидации ни RSS, ни резервная копия не создаются.

Запись идёт через временный файл в той же директории и атомарную замену. Lock-файл защищает от одновременных записей другими экземплярами CLI; перед записью также проверяется, не изменился ли исходный RSS после чтения. Symlink и специальные файлы как выход запрещены. Родительская директория результата должна существовать.

После аварийного завершения может остаться `rss.xml.maveton.lock`. Убедитесь, что указанный в нём PID больше не работает с фидом, затем удалите lock вручную. При работе разных программ с одним файлом всё равно требуется координация: сторонние редакторы не соблюдают lock CLI.

Восстановление: сначала сохраните неудачный текущий результат отдельно, затем скопируйте выбранную резервную копию на его место и выполните `validate`. Старые резервные копии CLI автоматически не удаляет.

## Дата публикации и GUID

Дата задаётся явно, с часовым поясом:

```yaml
publishedAt: '2026-11-06T12:00:00+03:00'
```

Нужны дата, часы, минуты и секунды. Поддерживаются `Z`, `+03:00` и `+0300`. Несуществующие даты и даты в будущем для нового выпуска отклоняются. В RSS время переводится в UTC и RFC 2822. Часовой пояс компьютера на результат не влияет.

Для публикации сейчас удалите `publishedAt` из описания и передайте:

```bash
maveton add --feed ./rss.xml --episode ./episode.yaml --output ./rss-next.xml --now
```

Одновременное использование `publishedAt` и `--now` — ошибка. `--now` определяет дату элемента RSS; это не публикация на сервер. Черновиков и планировщика нет. `liveItem status=pending` поддерживается как метаданные спецификации, но также не запускает трансляцию и не планирует обновление фида.

Идентификаторы выбираются в следующем порядке:

| Поле | Поведение |
| --- | --- |
| `guid` | Используется без изменений с `isPermaLink=false`; удобно при переносе известных идентификаторов |
| `id` | Рекомендуемый вариант: постоянный ID выпуска внутри подкаста, например `episode-042`; CLI получает из него детерминированный UUIDv5 |
| Ни `guid`, ни `id` | Детерминированный UUIDv5 из точной строки URL аудио |

`guid` и `id` взаимоисключающие. При использовании `id` в вычисление также входит идентичность подкаста: существующий `podcast:guid`, иначе адрес Atom `rel=self`, иначе `channel/link`. Не меняйте выбранную идентичность после публикации. Для старого фида без `podcast:guid` и меняющихся адресов безопаснее явно задавать GUID новых выпусков.

Для нового подкаста `podcast:guid` автоматически вычисляется по алгоритму Podcast Index из `feedUrl` с удалёнными схемой и завершающими `/`. Можно передать собственный UUIDv5 через `podcast` → `tag: guid`. В существующем RSS этот тег сохраняется.

Совпадение GUID **или URL основного аудио** с уже опубликованным выпуском блокирует добавление. Изменение названия и даты не обходит проверку. Режима `update` нет; не пытайтесь обходить защиту новым `id` для того же аудиофайла. При повторной обработке одного задания в CI дубликат даёт код `1`, а не молчаливый успех.

## Формат данных подкаста

Минимальный `podcast.yaml`:

```yaml
title: Мой подкаст
description: О чём и для кого этот подкаст.
link: https://example.com/podcast
feedUrl: https://example.com/rss.xml
language: ru
author: Имя автора
explicit: false
image: https://example.com/cover.jpg
owner:
  name: Имя владельца
  email: podcast@example.com
categories:
  - name: Technology
```

| Поле | Обязательное | Значение |
| --- | --- | --- |
| `title` | Да | Название |
| `description` | Да | Непустое описание, предпочтительно обычный текст |
| `link` | Да | HTTPS-сайт подкаста |
| `feedUrl` | Да | Постоянный публичный HTTPS-адрес будущего RSS; записывается в `atom:link` |
| `language` | Да | BCP 47: `ru`, `en`, `en-US` и т. п. |
| `author` | Да | Автор/организация → `itunes:author` |
| `explicit` | Да | YAML/JSON boolean `true` или `false`, без кавычек |
| `image` | Да | HTTPS-ссылка на обложку; также создаётся стандартный RSS `image` |
| `owner.name`, `owner.email` | Да | Контакт владельца; станет публичным в RSS |
| `categories` | Да | Непустой массив `{name, subcategory?}`; точные английские названия Apple, регистр важен |
| `type` | Нет | `episodic` по умолчанию либо `serial` |
| `copyright` | Нет | Строка копирайта |
| `podcast` | Нет | Массив тегов Podcasting 2.0 уровня channel |

Категории задаются английскими значениями даже для русскоязычного шоу. Например: `Society & Culture` → `Relationships`. Список проверяется локально. До двух основных категорий рекомендуется для совместимости Apple; более двух даёт предупреждение.

## Формат описания выпуска

Минимальный `episode.yaml`:

```yaml
id: episode-001
title: Первый выпуск
description: Описание первого выпуска.
publishedAt: '2026-01-01T12:00:00+03:00'
enclosure:
  url: https://example.com/audio/001.mp3
  length: 32000000
  type: audio/mpeg
duration: 2000
```

| Поле | Обязательное | Значение |
| --- | --- | --- |
| `title`, `description` | Да | Непустые строки |
| `enclosure.url` | Да | HTTPS URL основного аудиофайла |
| `enclosure.length` | Да | Положительное целое число — точный размер в байтах; не строка |
| `enclosure.type` | Да | `audio/mpeg` для MP3; `audio/mp4` для AAC в MP4, также принимается `audio/x-m4a` |
| `publishedAt` | Да, кроме `--now` | ISO 8601 с часовым поясом, не в будущем |
| `id` / `guid` | Нет | Постоянный идентификатор, см. правила выше |
| `duration` | Нет, рекомендуется | Положительное целое число секунд; отсутствие даёт предупреждение |
| `explicit` | Нет | Boolean; наследуется от подкаста |
| `episode` | Для полного выпуска serial-шоу | Положительный целый номер выпуска → `itunes:episode` |
| `season` | Нет | Положительный целый номер сезона → `itunes:season` |
| `episodeType` | Нет | `full` по умолчанию, `trailer` или `bonus` |
| `link` | Нет | HTTPS-страница выпуска |
| `author` | Нет | Автор именно этого выпуска |
| `image` | Нет | HTTPS-ссылка на отдельную обложку |
| `contentHtml` | Нет | Расширенная аннотация → `content:encoded` |
| `podcast` | Нет | Теги Podcasting 2.0 уровня item |

Если новый выпуск имеет `explicit: true`, а подкаст — `false`, CLI меняет канал на `true` и сообщает об этом в плане/отчёте. Старые эпизоды не меняются. Если `explicit` выпуска отсутствует, применяется текущее значение канала.

Размер аудио необходимо получить у хостинга или из исходного файла. Если локальная копия совпадает с опубликованной, на macOS и Linux можно выполнить:

```bash
wc -c < ./episode-001.mp3
```

CLI не скачивает медиа и не подставляет выдуманный размер или длительность. Основной `enclosure` рассчитан на общую аудиосовместимость платформ; Opus, видео, HLS, IPFS и другие варианты можно описать в `podcast:alternateEnclosure`.

JSON использует те же поля и типы. Неизвестные поля на верхнем уровне, дубли ключей, YAML aliases и неподдерживаемые YAML-теги отклоняются. Все файлы — UTF-8. Лимит YAML/JSON — 2 MiB; числовые значения должны помещаться в безопасный диапазон целых JavaScript.

### HTML и экранирование

```yaml
contentHtml: |
  <p>Обсуждаем <strong>новый выпуск</strong>.</p>
  <ul>
    <li><a href="https://example.com/materials">Материалы</a></li>
  </ul>
```

Передавайте обычный текст и HTML как есть. Символы `&`, `<`, `>` экранируются XML-сериализатором. Предварительное XML-экранирование приведёт к двойному экранированию. Это не HTML-санитайзер: используйте простые абзацы, списки и ссылки, без скриптов и встроенных виджетов. Отображение аннотации зависит от приложения.

## Podcasting 2.0

Все утверждённые теги доступны через единый формат:

```yaml
podcast:
  - tag: person
    text: Анна
    attributes:
      role: guest
      href: https://example.com/anna
  - tag: transcript
    attributes:
      url: https://example.com/episode.vtt
      type: text/vtt
      language: ru
      rel: captions
  - tag: alternateEnclosure
    attributes:
      type: audio/opus
      length: 24000000
      title: Opus
    children:
      - tag: source
        attributes:
          uri: https://example.com/episode.opus
```

Элементы `podcast` в `podcast.yaml` попадают в `channel`, а в `episode.yaml` — в новый `item`. Имена `person` и `podcast:person` равнозначны. `attributes` содержит строковые/числовые/boolean значения, `text` — текст/число/boolean, `children` — массив вложенных тегов. Порядок и повторения сохраняются; произвольный сырой XML не требуется.

Для стандартных дочерних тегов `liveItem` используйте явный префикс `rss:`: например, `rss:title`, `rss:guid`, `rss:enclosure`. Он служит только обозначением входного формата: в XML получится обычный `<title>`, `<guid>` или `<enclosure>` без namespace. Также доступны `itunes:`, `content:` и `atom:`. Переопределение namespace через входные атрибуты запрещено.

Ключевые примеры:

- [podcast-full.yaml](examples/podcast-full.yaml) — channel, люди, география, финансирование, podroll, publisher, чат, изображения и liveItem.
- [episode-full.yaml](examples/episode-full.yaml) — все теги уровня item, альтернативные источники, подпись, платежные доли и временные интервалы.
- [PODCASTING2.md](docs/PODCASTING2.md) — полный список допустимых родителей, обязательных и необязательных атрибутов.

Проверка примеров:

```bash
maveton add \
  --podcast examples/podcast-full.yaml \
  --episode examples/episode-full.yaml \
  --output ./full.xml \
  --dry-run
```

Полный пример специально содержит устаревший `images`, поэтому даёт предупреждение; с `--strict` это будет код `1`. Удалите этот тег при подготовке нового подкаста, заменив его `image`.

`podcast:season` и `podcast:episode` задаются отдельно от полей `season` и `episode`, создающих iTunes-теги. Это позволяет использовать название сезона и дробный номер `podcast:episode`, сохраняя целочисленный номер для iTunes. Значения автоматически не синхронизируются.

`person` на уровне эпизода заменяет весь состав людей уровня подкаста в совместимых приложениях: при добавлении гостя перечислите также ведущих. Платёжные блоки описывают метаданные и не отправляют деньги; доли — относительные веса, их сумма не обязана равняться 100. `podping usesPodping=true` не включает отправку уведомлений; задавайте его лишь при наличии отдельной работающей интеграции.

Существующие сторонние XML-расширения сохраняются. Неизвестный тег/атрибут в namespace Podcasting 2.0 выдаёт предупреждение: это может быть опечатка или более новая версия спецификации. Для CI используйте `--strict`, чтобы такие случаи требовали внимания.

## Валидация и границы результата

```bash
maveton validate --feed ./rss.xml
maveton validate --feed ./rss.xml --strict
maveton validate --feed https://example.com/rss.xml --json
```

Валидатор проверяет XML, единственный RSS 2.0 channel, обязательные метаданные общего профиля, категории, языковой тег, типы и значения полей, даты, GUID, дубликаты URL аудио, структуру Podcasting 2.0, обязательные атрибуты, кардинальность и ограничения вложенных блоков.

Для некоторых полей проверяется формат, а не фактическое существование: например, страна в `location` — два заглавных символа, OSM — форма идентификатора, платежный адрес — синтаксис. RRULE проверяется по компонентам и основным связям между ними, но календарь публикаций не вычисляется. Полная криптографическая проверка `integrity`, проверка владения адресом и содержимого внешних файлов не выполняются.

**Локальная успешная проверка не означает гарантированное принятие платформой.** В отчёте всегда явно указано `scope: local` и перечислены непроверенные области. В согласованном режиме нет запросов к аудио, обложкам, главам, транскриптам или платёжным системам. Если `--feed` — URL, скачивается только сам RSS; для полностью офлайн-работы передайте локальный файл.

Перед публикацией отдельно обеспечьте публичную доступность RSS и медиа, корректную обложку, поддержку сервером HEAD и Range, соответствие кодека MIME-типу и действительность `enclosure.length`. Размеры/цветовое пространство изображений, контентные требования, права, модерация, подтверждение контакта владельца и региональная доступность проверяются платформами. [Технические требования Apple](https://podcasters.apple.com/support/823-podcast-requirements), [спецификация Spotify](https://support.spotify.com/us/creators/article/podcast-specification-doc/), [RSS-импорт YouTube](https://support.google.com/youtube/answer/13525207?hl=en).

Для YouTube Music используется импорт аудиоподкаста через YouTube Studio, где это доступно. RSS не заменяет загрузку нативного видео; импорт и управление опубликованным подкастом выполняются на стороне YouTube. [Описание RSS-импорта](https://support.google.com/youtube/answer/13525207?hl=en).

`add` валидирует **весь получившийся фид**, включая историю, до записи. Если старые выпуски не соответствуют общему профилю, добавление блокируется. CLI не исправляет их молча. Некоторые допустимые для отдельного RSS-клиента значения могут быть строже ограничены общим профилем: например, основной видео-enclosure или старые варианты `itunes:explicit=yes/no/clean`.

## Предпросмотр, stdout и JSON

`--dry-run` выполняет подготовку и валидацию, показывает GUID, число выпусков до/после и изменения explicit; файлы и резервные копии не создаются. Права на запись и доступность выходной директории при этом не проверяются — эти ошибки возможны при фактическом сохранении.

Чтобы увидеть полный XML без записи:

```bash
maveton add --feed ./rss.xml --episode ./episode.yaml --output - --dry-run
```

Чтобы сохранить XML через shell:

```bash
maveton add --feed ./rss.xml --episode ./episode.yaml --output - > ./preview.xml
```

**Не направляйте stdout в исходный файл:** shell обнулит его до запуска CLI. Для изменения `rss.xml` используйте `--output ./rss.xml --overwrite`. При перенаправлении stdout защитой файлов и резервными копиями управляет shell, а не CLI.

Без `--json` сообщения и диагностика идут в stderr; stdout зарезервирован для XML (`--output -`), справки и версии. С `--json` stdout содержит один JSON-объект. `--json` и `--output -` несовместимы.

```bash
maveton add --feed ./rss.xml --episode ./episode.yaml --output ./next.xml --dry-run --json
maveton validate --feed ./rss.xml --strict --json > ./validation.json
```

Пример успешного отчёта валидации (поле `unchecked` здесь сокращено):

```json
{
  "ok": true,
  "command": "validate",
  "valid": true,
  "errors": 0,
  "warnings": 0,
  "episodes": 2,
  "issues": [],
  "scope": "local",
  "unchecked": ["Реальный размер, кодек и длительность аудио"]
}
```

`valid` означает отсутствие ошибок проверки; `ok` также учитывает `--strict`. Поэтому при предупреждениях возможны `valid: true`, `ok: false` и код выхода `1`. Ошибки аргументов, чтения или записи имеют вид `{ "ok": false, "error": { "code": "...", "message": "..." } }`. Отчёт `add` содержит `plan`, `validation`, а при записи — `written.output` и при перезаписи `written.backup`.

| Код выхода | Значение |
| --- | --- |
| `0` | Успех; предупреждения допустимы без `--strict` |
| `1` | Невалидный RSS/XML, дубликат выпуска или предупреждения в `--strict` |
| `2` | Неверные аргументы/описание YAML/JSON, файловая или сетевая ошибка |

## Использование в CI

Зафиксируйте YAML/JSON, исходный RSS и `package-lock.json` в репозитории. Рабочий сценарий: проверить исходные материалы, построить новый файл, проверить его, сохранить как артефакт, затем отдельно опубликовать утверждённый результат.

```bash
npm ci
npm run build
mkdir -p build

node dist/cli.js add \
  --feed ./podcast/rss.xml \
  --episode ./episodes/042.yaml \
  --output ./build/rss.xml \
  --strict --json > ./build/add-report.json

node dist/cli.js validate \
  --feed ./build/rss.xml \
  --strict --json > ./build/validation.json
```

В shell-скрипте добавьте `set -e`, чтобы остановиться на ненулевом статусе; либо явно обработайте код выхода каждой команды. Публикуйте только после успеха обеих команд. Используйте чистую директорию сборки, иначе защита от перезаписи остановит повторную сборку. Для воспроизводимой даты используйте `publishedAt`, а не `--now`; `lastBuildDate` отражает реальное время сборки.

Для нескольких подкастов храните отдельные `podcast.yaml`, RSS и каталоги эпизодов. Глобального конфигурационного файла, скрытого состояния и базы данных у CLI нет.

В проект включён workflow [.github/workflows/ci.yml](.github/workflows/ci.yml) для проверки кода на macOS/Linux и Node 24/26. Это проверка самого инструмента, не автоматическая публикация подкаста.

## Ограничения и устранение ошибок

| Код / ситуация | Что сделать |
| --- | --- |
| `DUPLICATE_EPISODE` | Убедиться, что выпуск ещё не опубликован; проверить `id`, `guid` и URL аудио |
| `INPUT_DATE`, `INPUT_FUTURE` | Указать существующую прошедшую дату с поясом либо удалить `publishedAt` и использовать `--now` |
| `ENCLOSURE_LENGTH` | Указать реальный положительный размер файла в байтах |
| `PODCAST_PARENT`, `PODCAST_CHILD_REQUIRED` | Проверить уровень тега и вложенность по справочнику |
| `PODCAST_UNKNOWN_TAG` / `PODCAST_UNKNOWN_ATTRIBUTE` | Проверить регистр/опечатку; при новом стандарте обновить зафиксированные правила |
| `ITUNES_CATEGORY` | Использовать точное английское значение категории, включая регистр |
| `OUTPUT_EXISTS` | Выбрать новый путь или передать `--overwrite` для создания backup |
| `SOURCE_CHANGED`, `OUTPUT_CHANGED` | Прочитать свежую версию фида и повторить операцию |
| `OUTPUT_LOCKED` | Дождаться другого процесса; после аварии проверить PID и удалить оставшийся lock |
| `OPERATION_FAILED` | Проверить путь, права, свободное место, TLS и доступность сервера |

Удалённый RSS: только HTTPS, максимум пять перенаправлений (без перехода на HTTP), таймаут 30 секунд на загрузку и перенаправления, максимум 20 MiB в распакованном виде. Локальный RSS ограничен тем же размером. DTD и объявления сущностей запрещены. Максимальная глубина XML — 64, структуры входных расширений — 32.

При сохранении сериализуется весь XML DOM: семантика старых элементов, namespace, комментарии и CDATA сохраняются, но оформление XML, расположение namespace-деклараций и вид экранирования могут измениться. Побайтовой идентичности всего RSS нет; исходные байты остаются в резервной копии.

## Разработка

```bash
npm run dev -- --help
npm run build
npm run lint
npm test
npm run check
npm run docs
npm pack --dry-run
```

Тесты используют встроенный Node test runner: создание/добавление/валидация, стабильность GUID, дубликаты, неизвестные namespace, все теги Podcasting 2.0, ошибки структуры, кодировки и даты, безопасность записи, резервные копии, конкуренция, dry-run, JSON/exit codes, границы загрузки и перенаправления. HTTP-ответы в тестах моделируются локально; внешние сервисы и медиа не нужны.

Код разделён на разбор входных описаний (`input.ts`), работу с XML (`xml.ts`), создание/добавление (`feed.ts`), правила Podcasting 2.0 (`podcast.ts`), валидацию общего профиля (`validate.ts`), файловый/сетевой ввод-вывод (`io.ts`) и CLI (`cli.ts`).

При обновлении Podcasting 2.0 сопоставьте официальный `docs/1.0.md` со списком в `podcastRules`, обновите правила и локальные реестры, примеры, тесты, справочник и commit в `docs/SOURCES.md`. Предложения из `proposal-docs` не считаются утверждённой спецификацией, пока не включены в основной документ.

В `package.json` зафиксированы overrides `minimatch >=11.0.1` для ESLint и typescript-eslint: это исправление опубликованной уязвимости транзитивных dev-зависимостей. При обновлении инструментов проверьте, нужны ли overrides, и выполните `npm run check` и `npm audit`. На рабочие зависимости CLI они не влияют.
